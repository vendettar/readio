## 1. Persistence Layers

Cloud now has two distinct persistence layers that must not be conflated:

- browser-local persistence in the frontend
- backend SQLite persistence in `apps/cloud-api`

## 2. Frontend Browser-Local Persistence

Cloud frontend still uses IndexedDB and localStorage for browser-owned state.

- IndexedDB: metadata, sessions, downloads, subtitles, browser-local library state
- localStorage: lightweight non-sensitive settings only
- credentials table: browser-local provider credentials when applicable

Important constraint:

- Cloud backend still does not replace the browser-local library model.
- Favorites, subscriptions, history, downloaded tracks, and local transcript artifacts remain local to the browser.
- Clearing site data still removes them.

## 3. Settings and Credentials Boundary

Settings and credentials are separate data classes.

- Non-sensitive preferences may live in settings/localStorage when they are explicitly browser-public behavior.
- Provider credentials must live only in the browser-local `credentials` table or in transient runtime memory for the active session.
- There must be no localStorage/sessionStorage fallback for provider credentials.
- If IndexedDB is unavailable when credentials are required, the feature must fail explicitly instead of silently falling back to weaker storage.
- Runtime environment defaults may prefill in-memory values, but they must not create persisted credential rows without an explicit user save.

Credential import/export/wipe rules:

- Exported user data must not include provider credentials.
- Imported settings must not overwrite existing credentials unless the import format explicitly defines a credential flow.
- "Wipe all" operations must invalidate or sequence-guard in-flight writes so stale async work cannot recreate deleted settings or credentials.

## 4. Backend SQLite Persistence

Cloud backend now also owns server-side SQLite persistence for backend-governed features.

Backend-owned SQLite responsibilities include:

- built-in ASR quota / reservation / idempotency state
- PodcastIndex-derived podcast show and episode snapshots for Cloud discovery page rendering:
  - `podcast_shows`: podcast/show domain metadata
  - `podcast_episodes`: bounded retained episode rows, ordered by stable newest-first sort
  - `podcast_cache_state`: refresh, backoff, truncation, eviction, and access metadata
- shared podcast transcript asset metadata and file ownership for eligible podcast episodes
- other backend-owned operational state that must survive process restarts

Discovery snapshot constraints:

- `podcast_shows` must not store cache-state fields such as refresh timestamps, failure counters, byte estimates, or eviction priority.
- `podcast_episodes` is the source for retained episode count and latest retained publish time; route totals use `COUNT(*)`, and incremental refresh selects the latest retained row with `ORDER BY published_at_unix DESC LIMIT 1`.
- `podcast_cache_state` owns cache metadata only. It is not user library state and is not a full historical archive contract.
- PodcastIndex cache SQL is generated with sqlc from `apps/cloud-api/internal/db/schema.sql` and `apps/cloud-api/internal/db/queries/pi_episode_cache.sql`; regenerate it with `go generate ./internal/db` from `apps/cloud-api`. `apps/cloud-api/internal/podcastindex/cache_store.go` keeps transaction orchestration and maps generated rows into domain structs.

Non-goals:

- backend SQLite is not the owner of RSS feed XML parsing or feed-route cache state
- `/api/v1/discovery/feed` is not part of the active Cloud API surface

This backend SQLite layer is not a generic replacement for browser-local user library data.

## 5. Runtime Cache Ownership

Discovery/search frontend persistence uses memory-backed server-state caching rather than a long-lived browser-local discovery archive.

- frontend discovery relies on TanStack Query memory cache
- active backend discovery routes rely on backend-managed in-memory cache where applicable; PodcastIndex podcast detail / episode-list reads use the SQLite snapshot tables above
- `runtime_cache` still exists for remaining browser-local runtime caches that still have owners

## 6. Browser-Local Consistency Rules

- Browser-local repositories should own schema access, validation, and write ordering for their tables.
- UI components must call store/repository actions instead of writing IndexedDB directly.
- Async writes that follow a destructive action, such as clearing data or wiping credentials, must be guarded by an epoch/request sequence or equivalent stale-write protection.
- Download, transcript, and playback records may reference local blobs only inside the browser that owns those blobs.

## 7. Backend SQLite Governance Summary

All backend SQLite features in Cloud must follow the same operational rules:

- schema changes must go through versioned SQL migrations
- `goose` is the migration mechanism
- backend startup must apply pending migrations before serving requests
- no route-local or feature-local ad hoc DDL
- production and tests must rely on the same schema path
- source-of-truth tables and helper/derived state must be documented explicitly

The detailed backend rules live in [Backend SQLite Governance](/apps/cloud/handoff/backend-sqlite-governance).

## 8. Key Frontend Tables Still Relevant to Cloud UI

These browser-local tables still matter to Cloud UI behavior:

- `sessions`
- `audioBlobs`
- `subtitles`
- `remote_transcripts`
- `folders`
- `tracks`
- `local_subtitles`
- `subscriptions`
- `favorites`
- `settings`
- `credentials`
- `runtime_cache`

## 9. Documentation Boundary

Cloud docs must describe persistence ownership honestly:

- no account sync for browser-local library state
- no server-backed recovery for browser-local-only data
- no claim that backend SQLite is a user archive unless a feature explicitly defines that contract
- repo-owned Cloud runtime contracts do not persist or key library state by feed transport fields
