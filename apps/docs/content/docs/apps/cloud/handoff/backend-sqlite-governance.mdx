title: Backend SQLite Governance
---

## 1. Purpose

This document records the long-lived SQLite rules for Cloud backend features.

These rules are not tied to a single feature implementation. They are the shared persistence contract for backend-owned state such as ASR usage governance, PodcastIndex discovery snapshots, and shared transcript asset metadata.

## 2. Migration Contract

All backend SQLite schema creation and evolution must follow one path:

- versioned SQL migrations in `apps/cloud-api/migrations`
- `goose` as the migration runner
- startup-time migration application before request serving
- no ad hoc `CREATE TABLE IF NOT EXISTS` or feature-local schema bootstrap

Production code, local development, and tests must depend on the same migration path. A test-only schema path is not acceptable.

## 3. Bootstrap Contract

An empty database is valid if the schema exists and zero rows are present.

That means:

- startup may create/apply schema, but does not need to seed feature rows
- feature code must handle empty-table bootstrap states cleanly
- absence of rows is not itself a corruption signal
- `READIO_CLOUD_DB_PATH` is required runtime configuration, must be absolute, and `apps/cloud-api` does not fall back to a release-local default database path
- the deployer must pre-create the parent directory of `READIO_CLOUD_DB_PATH`; `apps/cloud-api` fails fast if that directory is missing
- Cloud startup order is `open -> initial ping -> runtime pragmas -> migrations -> ready`
- the current runtime keeps one open SQLite connection, and also encodes `foreign_keys=ON`, `busy_timeout=5000`, and `synchronous=NORMAL` in the DSN so any later connection inherits the same baseline; `journal_mode=WAL` is established in the ordered startup path before migrations

## 4. Source Of Truth Discipline

Every backend SQLite feature must define which tables are authoritative and which state is derived.

Rules:

- source-of-truth tables own correctness
- helper tables, projections, counters, or cached summaries must not silently become authoritative
- if helper state is rebuilt, rebuild logic must derive from authoritative rows
- docs must say when a feature is a bounded cache/snapshot rather than a canonical archive

## 5. ASR Persistence Rules

Built-in ASR persistence is backend-owned operational state.

The durable contract includes:

- request identity / idempotency tracking
- reservation lifecycle states such as `reserved`, `consumed`, `released`, and `failed`
- deterministic usage accounting for the deployment-wide quota window
- cleanup of abandoned or stale reservations by transitioning them to a terminal released state instead of leaving them indefinitely in-flight

Built-in ASR SQLite storage is not a transcript archive and does not own raw audio or transcript text persistence.

Shared podcast transcript assets use a separate persistence contract:

- the request/quota/idempotency ledger remains distinct from transcript asset identity
- SQLite is authoritative for transcript asset metadata, reuse lookup identity, and file ownership metadata
- the canonical transcript payload is a compressed `json.gz` file under deployment-owned `PODCASR_TRANSCRIPTS_DIR`
- shared transcript assets require both `itunes_id` and `episode_guid`; there is no fallback identity path
- the metadata table stores `file_name` only, not a relative path or inline transcript body
- retention is permanent by default; no automatic GC or TTL is defined

## 6. Shared Transcript Asset Rules

Shared podcast transcript assets are backend-owned reusable content artifacts, not request-local retry blobs.

Rules:

- SQLite stores asset metadata and lookup classifiers, not the canonical transcript JSON body
- the filesystem stores the canonical compressed cue payload in `json.gz` form
- runtime absolute file paths are derived from `PODCASR_TRANSCRIPTS_DIR + "/" + itunes_id + "/" + episode_key + "/" + file_name`
- `episode_key` must derive directly from normalized `episode_guid`; normalization means trim outer whitespace and lowercase the full identity before hashing, without depending on frontend route encoding
- `source_kind` is stored as backend-provided classifier metadata; SQLite does not enforce enum membership or source-kind-driven nullability rules
- reuse lookup stays non-unique; one episode may retain multiple transcript assets for the same classifier tuple

## 7. PodcastIndex Snapshot Rules

PodcastIndex discovery persistence is a backend cache/snapshot layer, not a canonical long-term archive and not RSS feed XML parsing storage.

The durable contract includes:

- `podcast_shows` show metadata
- bounded `podcast_episodes` rows for retained episode windows
- `podcast_cache_state` freshness, backoff, truncation, eviction, and access metadata
- paging over the retained PodcastIndex snapshot window
- explicit freshness and refresh behavior owned by backend policy

Important boundary:

- deep pagination only guarantees access to the retained snapshot window
- docs must not imply full historical episode coverage unless the stored contract truly provides it
- docs must not describe `/api/v1/discovery/feed`, RSS feed parsing, or feed-route cache state as active backend SQLite responsibilities

If response shapes do not expose retention boundaries clearly, surrounding docs must still state that the route pages over the stored PodcastIndex snapshot, not over an infinite theoretical episode history.

## 8. Schema Design Expectations

Backend SQLite schema should encode important invariants where practical.

Examples:

- primary keys and unique indexes for stable identities
- foreign keys where ownership is explicit
- `CHECK` constraints for booleans or bounded enums when that reduces invalid state
- explicit timestamps for freshness and lifecycle transitions

This does not mean every product rule belongs in SQL, but invalid low-level states should not be left entirely to application convention when the schema can guard them cheaply.

## 9. Documentation Rule

If a new backend SQLite feature lands, its owner must update Cloud docs with:

- what the database is authoritative for
- what it is not authoritative for
- how schema changes ship
- whether the stored data is archival, bounded-cache, or operational-ledger state
