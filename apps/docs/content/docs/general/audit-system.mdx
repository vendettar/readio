---
title: Audit System
---

This document defines the default review posture for Readio code and documentation work. It applies when a task asks for a review, audit, improvement review, refactor review, or when completed work needs a second pass.

## 1. Review Role

The reviewer evaluates existing changes. It does not implement fixes unless the user explicitly asks for fixes after the review.

Default outcome:

- identify correctness, architecture, security, performance, product, documentation, and test risks
- cite concrete files, lines, commands, or behavior as evidence
- distinguish blocking defects from optional improvements
- avoid speculative future work that is not implied by the changed surface

## 2. Scope Selection

- If the user provides a commit range, review exactly that range.
- If the user asks for staged files, review `git diff --staged`.
- If the user asks for the current worktree, review tracked uncommitted changes and relevant new files.
- If the user asks for a full-repo audit, expand scope deliberately and state the boundaries.
- Otherwise, default to the latest task/commit and any directly related files needed to understand it.

Review the smallest scope that can answer the question honestly. Escalate only when evidence shows the change crosses a wider boundary.

## 3. Generated and Derived Files

- Treat generated files as generated and avoid stylistic findings there.
- For this repo, TanStack Router generated files such as `src/routeTree.gen.ts` should be checked only for correctness signals, such as missing routes caused by source misconfiguration.
- Generated SQL/client code should be reviewed through its source schema/query files unless the generated output reveals a real mismatch.

## 4. Review Priorities

Order findings by severity, not by personal preference.

1. Correctness and data integrity: broken behavior, stale writes, cancellation leaks, persistence ownership errors, migration/schema mismatches.
2. Security and privacy: exposed credentials, weak secret storage, unsafe logging/telemetry, authorization gaps.
3. API and contract compatibility: response shapes, error codes, runtime config allowlists, route ownership, cross-app contracts.
4. Architecture and maintainability: unclear ownership, path drift, unnecessary coupling, overbroad abstractions, stale documentation.
5. Performance and reliability: real render churn, unbounded memory/work, missing cleanup, retry/backoff mistakes.
6. UI, accessibility, and design system: primitive/token usage, keyboard/focus behavior, overlay semantics, loading/error consistency.
7. Test coverage: missing regression tests for changed behavior, especially aborted/stale async paths and destructive persistence flows.

## 5. Finding Format

Use concise findings that include:

- **Severity**: `P0` data loss/security outage, `P1` blocking correctness/regression, `P2` important but bounded, `P3` polish or maintainability.
- **Title**: one concrete problem.
- **Evidence**: file/line, diff hunk, command output, or observed behavior.
- **Impact**: what breaks for users, operators, contributors, or future agents.
- **Fix direction**: the smallest credible correction.
- **Verification**: the test, command, or manual check that would prove the fix.

Prefer one strong finding over several overlapping weak findings.

## 6. Review Cadence

- Default review: changed diff, test gaps, and one relevant risk area.
- Milestone review: architecture, product contract, non-functional risks, and documentation consistency.
- Full audit: only when requested or when a local finding proves the narrow scope cannot be assessed safely.

## 7. Output Shape

Lead with findings. If there are no findings, say that directly and mention residual risk or unrun tests.

Recommended structure:

## Findings
- Ordered by severity with file/line evidence.

## Open Questions
- Only questions that affect correctness or review confidence.

## Summary
- Short context on what was reviewed and what remains unverified.

## 8. Review Boundaries

- Do not modify code or docs during a review unless the user asks for fixes.
- Do not ask for broad rewrites when a targeted change would address the risk.
- Do not enforce frontend-only rules on backend, docs, or infrastructure work unless they actually apply.
- Respect the current project stage: first-release work may remove stale client-data migration obligations, but it must still protect current user data and credentials.
