---
title: 审计系统
---

本文定义 Readio 代码与文档工作的默认审查姿态。它适用于用户请求 review、audit、improvement review、refactor review，或已完成工作需要二次审查的场景。

## 1. 审查角色

Reviewer 评估已有变更。除非用户在审查后明确要求修复，否则不直接实现修复。

默认产出：

- 识别 correctness、architecture、security、performance、product、documentation 与 test 风险
- 用具体文件、行号、命令或行为作为证据
- 区分阻塞缺陷与可选改进
- 避免提出与 changed surface 无关的猜测性未来工作

## 2. 范围选择

- 如果用户提供 commit range，审查该确切范围。
- 如果用户要求审查 staged files，审查 `git diff --staged`。
- 如果用户要求审查当前 worktree，审查已跟踪的未提交变更和相关新文件。
- 如果用户明确要求 full-repo audit，才扩展范围，并说明边界。
- 否则默认审查最近任务/提交，以及理解它所需的直接相关文件。

使用能诚实回答问题的最小范围。只有证据表明变更跨越更宽边界时，才升级审查范围。

## 3. Generated 与 Derived Files

- 将 generated files 视为 generated，避免在那里提出样式类问题。
- 对于本仓库，TanStack Router 生成的文件，例如 `src/routeTree.gen.ts`，只检查正确性信号，例如源配置错误导致的路由缺失。
- 生成的 SQL/client code 应优先通过其 source schema/query 文件审查，除非生成结果暴露真实不匹配。

## 4. 审查优先级

按严重度排序，而不是按个人偏好排序。

1. Correctness 与 data integrity：行为破坏、stale write、cancellation leak、持久化 ownership 错误、migration/schema 不一致。
2. Security 与 privacy：凭据暴露、弱 secret 存储、不安全日志/telemetry、授权缺口。
3. API 与 contract compatibility：response shape、error code、runtime config allowlist、route ownership、跨 app 契约。
4. Architecture 与 maintainability：ownership 不清、path drift、不必要耦合、过宽抽象、过期文档。
5. Performance 与 reliability：真实 render churn、无边界内存/任务、缺失 cleanup、retry/backoff 错误。
6. UI、accessibility 与 design system：primitive/token 使用、keyboard/focus 行为、overlay 语义、loading/error 一致性。
7. Test coverage：变更行为缺少 regression tests，尤其是 aborted/stale async path 和破坏性持久化流程。

## 5. 问题格式

保持问题简洁，并包含：

- **Severity**：`P0` 数据丢失/安全事故级别，`P1` 阻塞性正确性/回归，`P2` 重要但有边界，`P3` 润色或可维护性。
- **Title**：一个具体问题。
- **Evidence**：file/line、diff hunk、命令输出或观测行为。
- **Impact**：对用户、运维、贡献者或后续 agent 的影响。
- **Fix direction**：最小可信修复方向。
- **Verification**：能证明修复的测试、命令或人工检查。

宁可保留一个强问题，也不要拆成多个重叠的弱问题。

## 6. 审查节奏

- 默认审查：changed diff、test gap 和一个相关风险区域。
- Milestone review：architecture、product contract、non-functional risks 与文档一致性。
- Full audit：仅在用户要求，或本地发现证明窄范围无法安全判断时执行。

## 7. 输出形态

先给 findings。若没有 findings，直接说明，并列出残余风险或未运行测试。

推荐结构：

## Findings
- 按严重度排序，附 file/line 证据。

## Open Questions
- 仅保留影响正确性或审查信心的问题。

## Summary
- 简短说明审查范围和仍未验证的内容。

## 8. 审查边界

- 除非用户要求修复，否则审查期间不修改代码或文档。
- 若定向修改足以消除风险，不要求大范围重写。
- 不把 frontend-only 规则强行套用到 backend、docs 或 infrastructure，除非它们确实适用。
- 尊重当前项目阶段：first-release 工作可以移除过期的客户端数据迁移义务，但仍必须保护当前用户数据与 credentials。
